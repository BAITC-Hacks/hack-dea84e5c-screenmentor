# Доступ и регистрация пользователей

**Статус:** целевая production-модель; не входит в текущий хакатонный режим 0.24.20.

## 1. Принцип

Пользователь не должен вручную вводить адрес backend, API-ключ или pairing-токен. Эти настройки остаются только в хакатонной и локальной конфигурации. В публичном продукте расширение получает пользовательскую сессию после простого входа, а backend проверяет персональный access token/JWT.

## 2. Обычный пользователь

### Вход по номеру телефона или email

1. Пользователь устанавливает расширение и выбирает язык.
2. На приветственном экране выбирает «Войти по телефону» или «Войти по email».
3. Получает одноразовый код подтверждения.
4. После ввода кода расширение автоматически получает сессию.
5. Backend применяет бесплатную квоту и ограничения скорости.

Пароль, API-ключ модели и адрес сервера пользователю не показываются. Сессию можно завершить кнопкой «Выйти»; refresh-токен отзывается на backend.

### Режим без регистрации

Пользователь может продолжить без аккаунта. В этом режиме действуют ограничения:

- небольшая квота запросов в день или месяц;
- ограничение голосовых минут и длины контекста;
- отсутствие истории между устройствами;
- отсутствие организационных сценариев и расширенной поддержки;
- обязательная защита от автоматического массового использования.

При исчерпании квоты панель объясняет, что можно войти по телефону/email или использовать код организации. Режим без регистрации не должен создавать неограниченные расходы для проекта.

## 3. Школы и учебные учреждения

Организация получает административный кабинет и код доступа, например `SCHOOL-2026-AB7K`.

1. Пользователь входит по телефону/email или продолжает без регистрации.
2. В панели выбирает «У меня есть код организации».
3. Вводит код или открывает invite-ссылку/QR-код.
4. Backend проверяет срок действия, лимит мест и разрешённые функции.
5. Пользователь получает организационную квоту.

Код организации не должен быть постоянным секретом администратора. Нужны срок действия, отзыв, лимит активаций и журнал только технических событий без содержания вопросов и страниц.

## 4. Подтверждение личности и социального статуса

Для сценариев, где требуется подтвердить категорию «школьник», «студент», «пожилой пользователь» или иной льготный статус, использовать только официальный поток eGov/ЭЦП либо другого уполномоченного identity-провайдера.

- ИИН не используется как пароль, логин или код доступа.
- Расширение не отправляет ИИН модели и не хранит его в IndexedDB.
- По возможности backend хранит только результат проверки, категорию, срок действия и непрямой идентификатор.
- Проверка нужна только при назначении льготы или организационного доступа, а не для каждой подсказки.
- Для несовершеннолетних нужен отдельный согласованный сценарий родителя/законного представителя.
- До запуска такого потока нужна отдельная юридическая и privacy-проверка: согласие, цель, срок хранения, удаление, трансграничная передача и права пользователя.

Это целевое направление, а не реализованная функция текущего прототипа.

## 5. Хакатонный режим

Для HackAlem AI сохраняется текущая схема:

- backend использует `LOCAL_ACCESS_TOKEN`;
- капитан/разработчик задаёт HTTPS-адрес и код подключения в popup;
- token хранится в IndexedDB расширения и не показывается после сохранения;
- API-ключ модели остаётся только на backend;
- отдельной регистрации конечных пользователей нет.

Хакатонный token нельзя выдавать публичным пользователям как постоянную систему аккаунтов. Он нужен для стенда, локальной разработки и технической проверки.

## 6. Целевой поток данных

```text
Телефон/email или eGov/ЭЦП
              ↓
       Auth-провайдер
              ↓ JWT / session
       ИИ Наставник backend
              ↓
       AI/STT/TTS провайдеры
```

Код организации проверяется backend до выдачи расширенной квоты. Модель получает только разрешённый UI-контекст и вопрос, но не паспортные сведения, ИИН, OTP, пароли или документы.

## 7. Этапы реализации

1. Добавить внешний Auth-провайдер с phone/email OTP.
2. Ввести пользователей, сессии, отзыв токенов и per-user rate limits.
3. Добавить анонимную квоту с device/session throttling.
4. Добавить таблицы организаций, кодов, сроков действия и лимитов.
5. Добавить административный invite-flow для школ.
6. Только после privacy/legal review изучать eGov/ЭЦП и подтверждение категорий.
7. Сохранить pairing-token как отдельный режим разработки и хакатона.

## 8. Критерий готовности

Пользователь должен открыть расширение и начать первую подсказку максимум за две понятные операции после установки. Ни один обычный пользователь не должен видеть `LOCAL_ACCESS_TOKEN`, API-ключ модели или внутренний адрес провайдера.
